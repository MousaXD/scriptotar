## Node 22 V8 non-backtracking RegExp fallback experiment — original unmodified 4.0.7 still vulnerable

**Do not use V8's experimental fallback flags as a release security workaround.** Original isolated Linux [Actions #44795623180](https://github.com/MousaXD/scriptotar/actions/runs/44795623180), workflow [`agent11-node-v8-nonbacktracking-fallback-experiment.yml`](https://github.com/MousaXD/scriptotar/blob/agent-11/p0-picomatch-candidate-evaluation-20261120/.github/workflows/agent11-node-v8-nonbacktracking-fallback-experiment.yml), exact test source `1879e381cab96ded17a57bc66203c2bf8bb4e4c8`, job `136494282492` **completed FAIL as a genuine unmitigated security result**, after guard, exact lock, npm and intended positive engine control had all passed. No parser modification, no npm override. Original source SHA and guard were checked before npm.

- Original experiment [#44795318837](https://github.com/MousaXD/scriptotar/actions/runs/44795318837) failed **at runtime setup** because Node 22 rejects `--enable-experimental-regexp-engine-on-excessive-backtracks` inside `NODE_OPTIONS`: `node: --enable-experimental-regexp-engine-on-excessive-backtracks is not allowed in NODE_OPTIONS`. It therefore did NOT execute original parser controls and is **not** attack evidence.
- Revised actual test explicitly used **Node CLI** `--enable-experimental-regexp-engine-on-excessive-backtracks --regexp-backtracks-before-fallback=1000` in isolated processes. The positive control `/(a+)+$/` against 36 `a` chars plus `!` passed under a hard 3-second timeout, establishing that the feature was functional for a supported backtracking regex.
- Actual original `picomatch@4.0.7` `makeRe` produced **lookaheads** (`(?=.)`) for all three vulnerable example globs: `+([ab]|b)`, `+(a*)`, `+(@(+([ab])))`. The V8 experimental fallback is documented to exclude regexes containing lookarounds. Each original `picomatch.isMatch(input,pattern)` executed directly under the same CLI V8 flags in an **individual killable 2-second child process**; **ALL THREE returned timeout exit 124** on the deliberate trailing mismatch inputs. Source-exact original compiled regex strings were printed in the runner log.
- **Result: 3/3 ORIGINAL hostile picomatch examples still TIMEOUT** despite the flags. Do not claim that Node engine fallback, `NODE_OPTIONS`, or a simple runtime upgrade resolves the real ReDoS behavior. A pure-regex positive control does not substitute for actual library performance or matcher semantics.

Official engine explanation: [V8 non-backtracking RegExp](https://v8.dev/blog/non-backtracking-regexp) documents lookahead/lookbehind incompatibility. The experiment is additional **mitigation rejection evidence**; the original 19/10/12 immutable corpora remain unchanged and the complete separately verified previous parser/compatibility failures still veto release.

## Decision tree for actual remediation

1. **Preferred:** an officially maintained picomatch version whose exact npm tarball, integrity, MIT/license, compiler and source provenance can be independently verified, and which passes original 19 plus expanded adversarial corpus and ALL original upstream matcher semantics without changing positive expected outcomes. Lock exact version and run all security/normal-build/platform tests. Agent10 independently reviews final SHA. No such version verified.
2. **Viable but substantial:** an independently maintained, semantics-preserving non-backtracking glob compiler/matcher that provides the actual documented APIs used by Vite, Vitest and tinyglobby, and that has proof/independent fuzzing on captures, options, negations, path handling, escaped classes and performance. Replace upstream transitive paths with **known trusted, reviewed** package distributions. A limited regex-rewrite proof of concept is *not* this.
3. **Mitigation-only:** keep the upstream original parser and comprehensively constrain externally controllable build patterns using immutable reviewed source trust policies, preserved package checks, and fail-closed CI workflows. Explicitly document that this does NOT fix a parser performance flaw; release decision requires separate Agent10 policy/security signoff and Agent00 authorization. None is present.
4. **Do not do:** unreviewed npm `overrides`, `npm audit fix` downgrades, silent `vitest`/Vite version changes, reclassifying withdrawn advisory as parser fix, suppressing the original 19 tests, changing expected matcher positives to false, synthetic CI success in lieu of real Linux/Windows installed app certification, or merging Agent11's experimental DRAFT PR157.

**Hard requirement: Release and issue #129 remain blocked unless a complete independently evidenced resolution or separately authorized risk decision emerges.**
